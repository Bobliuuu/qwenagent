# q11 (Track B): do private slots win when state capacity binds?

## Design (written before running)

Question. At P<=16 and d_s=64 a single shared state is not capacity-limited, so `multi` ~ `single` ~ `adapter` is expected. Shrink the per-slot width and push test P to 32/64 so a fixed-size shared state must hold P digits, and see whether slots (state that grows with P) win.

Setup (all cap cells): Qwen3-0.6B frozen, workers at layer 12, K=4 at train, train P in {2,3}, 6000 steps, ops/register 2-4, query task, random distinct 2-letter register names (`--long_names 1`, new flag, so names have the same format at P=2 and P=64; 676 names available), `occ=1`, `ret_norm=1` (the q9 setting), 3 seeds (0,1,2), 200 eval programs per P, test P in {2,3,4,8,16,32,64}. Chance 10%.

**`--match_params 0` for the whole sweep.** The usual flag widens single/adapter to multi's parameter count, which would hide a capacity bottleneck, so widths are set explicitly (new flag `--single_width`):

| variant | state | note |
|---|---|---|
| `multi` / `oracle` / `uniform` | K slots x d_s; at test K_eff = max(K, P), so total state = P*d_s | slots scale with P by construction (that is the claimed advantage) |
| `single_eq` | ONE state, width K*d_s (=4*d_s) | equal total state width to multi *at train* (K=4) |
| `single_ds` | ONE state, width d_s | the shrunken single (capacity-starved control) |
| `single_max` | ONE state, width 64*d_s | equal total width to multi *at P=64*, fixed at train. Only d_s in {4,8,16} (64*64=4096 too big) |
| `adapter` | stateless MLP, hidden 4*K*d_s | stateless reference |

So the fair comparison for "slots win when capacity binds" is multi vs single_max (equal state numbers at the largest P) and vs single_eq/single_ds (equal at train). Caveat: equal-at-test is not equal in parameters (GRU/phi params scale with width^2, so single_max has far more).

Sweep d_s in {4,8,16,64}. Pruned (cost cap ~$30): uniform only at d_s=4; single_max only d_s<=16; adapter only d_s=4; d_s=16 has no single_max in batch A; no multi_rr. Sequences at P=64 are ~1000 tokens; eval batch is 5 for P>16 (code change only affects P>16).

Part 2, ops-per-register wall: `--opr_curriculum "1,1:800;1,2:800;2,4:1200;4,8:1600;8,12:1800"` (up to 8-12 ops per register in training), train P in {2,3,4}, d_s=64, `single` (width 256 = K*d_s) / `multi` / `oracle`, match_params 0, same names/ret_norm setting. Eval via existing `P4_ops{5-6,7-12,13-24}` and P in {2,3,4,6}. Reference without curriculum (q9, 1-letter names): P4 at 5-6 ops ~0.19, 7-12 ~0.11, 13-24 ~0.12, i.e. near chance.

Code changes (additive only): `task.make(long_names=)`, `train.py --long_names --single_width`, eval batch 5 for P>16, `run_q11.sh`, `modal_cap.py` (app qwenagent-cap, volume qwenagent-cap-res).

### Run notes, nulls, dead seeds

- Batches: A (d_s=4 all variants, d_s=16 multi/oracle/single_eq/single_ds), B (opr wall x3, d_s=64 multi/oracle/single_eq/single_ds, uniform d_s=4), D (reruns). Batch C (d_s=8; single_max at d_s 8/16) was **never launched** (pruned for time/budget after A and B already gave a clear picture). Not run at all: multi_rr, single_max at d_s>=8, adapter at d_s 16/64, uniform at d_s>=16.
- **Dead seed:** `cap_single_max_d4` seed 1 never learned (13%/13% at P2/P3), which is why its std is huge. Its other two seeds are 59/51 and 60/49 at P2/P3. Kept in the means; excluding it would lift that row to roughly 59/50 at train P.
- **OOM crashes, rerun:** three processes sharing one 22 GB GPU OOM-ed on `cap_single_eq_d64` s0, `opr_multi` s2, `opr_oracle` s0 (long sequences, full-position logits). Re-run one-per-container as batch D with the same seeds; the logs in `logs/` are the successful reruns.
- Models are far from converged in-distribution (train-P accuracy 35-65%), so every cell is optimisation-limited, not just capacity-limited; read the extrapolation columns relative to P2/P3.
- The ops-wall experiment uses 2-letter names and the q9 setting (`ret_norm=1`), so its numbers are not directly comparable to the older 1-letter-name q9 runs, only roughly (q9 reference quoted in the design section).
- Cost: ~21 containers of A10G/L4/L40S, ~1-1.3 h each for the multi-type cells and well under that for single/adapter cells; estimated total around $15-20 (not metered from Modal billing). Smoke seed 9 result (`q11_cap_multi_d4_s9.json`) is a 200-step plumbing check, not a result.

## Verdict: do private slots win when capacity binds?

**No.** At no d_s and no P did learned-routing `multi` beat a single shared state or the stateless adapter outside seed noise, and for most of the grid it lost.

- **Shrinking the state does not make a shared state fail.** A single GRU of width 4 (`single_ds_d4`, 88k params, equal to multi's) scores 51/44/40/29/21/14 at P=2/4/8/16/32/64 versus multi_d4's 40/36/32/24/16/15: single is better at every P up to 32 and tied at 64. Width 16 (`single_eq_d4`) is better still (58/47/46/35/23/20). The stateless adapter at hidden width 16 (`adapter_d4`) is the best row at P<=16 (63/52/50/35/27/19). The workers are not storing 32-64 register values in a few floats: whatever the frozen Qwen does with context attention is carrying the tracking, and the injected module is a small nudge, so there is no state-capacity bottleneck for slots to relieve at these widths.
- **Equal-total-width controls agree.** multi vs single_eq (equal width at train, K*d_s) at P=64: d4 15 vs 20, d16 17 vs 19, d64 23 vs 17. multi vs single_ds at P=64: 15 vs 14, 17 vs 20, 23 vs 21. The single exception, multi_d64 at P=64 (23±2 vs 17±2 for single_eq_d64, 21±4 for single_ds_d64), is +2 to +6 points on 3 seeds at a P where everything is within ~13 points of chance, and it is reversed at P<=16. I do not count it as a win. The strict equal-at-P=64 single (`single_max`, width 64*d_s) only exists at d_s=4 and has a dead seed; it is 16±4 at P=64, i.e. not better than the width-4 single.
- **Routing is not the bottleneck either:** oracle (perfect binding) is not better than learned multi at d_s=4 or 64 (13 vs 15 and 15 vs 23 at P=64) and is only ahead of learned multi on train-range P at d_s=16 (58/48 vs 42/35), which is seed instability in multi (d_s=16 multi has per-seed P3 of 47/28/32), not a separation effect. uniform (no routing) at d_s=4 is as good as multi (13 at P=64, better at P<=16).
- **Where might slots still win?** Not shown anywhere here. A regime where they could is one that is not state-width-bound but binding-bound with a much stronger/longer-trained worker; this sweep says the 0.6B host with a layer-12 injection is not in a capacity-limited regime for d_s>=4. Untested: d_s<4, single_max at larger d_s, longer training, d_s=8.

### Ops-per-register wall (opr_curriculum up to 8-12 ops/reg), P in {2,3,4} training, d_s=64

The curriculum did **not** break the wall. P=4 with 5-6 / 7-12 / 13-24 ops per register: single 22/16/16, multi 18/11/15, oracle 20/20/20 (3 seeds; chance 10, q9 no-curriculum reference ~19/11/12). In-distribution accuracy on P2-4 also fell (single 36/38/32, multi 29/26/26 with high seed spread, oracle 36/38/39) compared with the no-curriculum cap runs at the same d_s (~55/47/48), so the curriculum made fitting worse inside the budget (6200 steps total over 5 phases) without buying length generalisation. Oracle binding is the only variant that holds a flat ~20% (about 2x chance) out to 13-24 ops, versus 11-16% for single and multi; with 3 seeds and std up to 4 this is a weak hint that perfect separation helps a little on long chains, not a result. Longer chains remain at or near chance for every mode.
